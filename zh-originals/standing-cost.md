# STANDING-COST — 固定成本體檢 Prompt（可重跑）
> 制定 2026-08-20（D047）。宗旨：盤點「每一輪請求都要付」的固定 context——常駐指令檔＋工具定義，逐項問「這條每輪的固定成本值不值得」。可重跑，非一次性任務。
> **與 `ops/RULE-AUDIT.md` 分工（兩支不可互相取代）：** 那支管**正確性**（這條還成立嗎／AI 查得到嗎），本檔管**重量**（每輪成本值不值得）。同一個檔案可以兩支都跑——一條規則完全正確、但一年只用到兩次，RULE-AUDIT 會留它，本檔會建議搬到按需載入層。本檔不做正確性稽核；量測中撞到事實錯誤，文末一行帶過，交 RULE-AUDIT 管轄。

## §0 觸發時機（比照 RULE-AUDIT §0，符合任一即該跑）
- 換模型世代（DISPATCH.md §0 模型現況表一動）。
- 裝了新 MCP server 或新常駐工具／skill／agent。
- 久未跑（距上次本體檢 >3 個月）。
- 額度消耗與工作量明顯對不上時。

## §1 盤點範圍（兩層都要盤，漏一層即失真）
**A｜指令檔層**：全域 `~/.claude/CLAUDE.md`、專案 CLAUDE.md 鏈、output style、hook 注入內容（OPS-CORE／BRAIN 全文／記憶喚醒摘要／進行中交接票）、agent/skill descriptions。每項必標「session 啟動即載」還是「按需載入」——被 shadow 掉或按需的檔不算固定成本。
**B｜工具定義／MCP server 層**（D045 漏盤的一層，本檔存在的主因）：逐一列掛載的 MCP server 與內建工具，記 server instructions 重量＋tool 數，並判定 tool schema 是**常駐進請求**還是 **deferred（要 ToolSearch 才載入）**——deferred 的常駐成本近乎零。⚠️「MCP 通常是最大單筆」是坊間通則，2026-08-20 首跑實證在本機不成立；要實測，不照抄結論。

## §2 逐項三評分
1. **Weight 重量**：估算 token 成本；每輪都付，還是碰到其範圍才付。
2. **Hit rate 命中率**：對使用者在這個資料夾實際做的工作，多大比例的請求用得到。先問使用者「這裡平常做哪幾類工作／有沒有確定要留的」再評，不得憑「同類專案通常需要」推定。
3. **Cost of being wrong 錯了的代價**：拿掉會壞什麼。防資料損失／安全／靜默錯誤的規則，再重也留——重量永遠不壓過這條。

## §3 三判決＋排序
- **Keep**：命中率撐得起重量，或錯了代價高。
- **Turn off / unload**：對本資料夾的工作命中率趨零。
- **Move to on-demand**：內容值得留但不必每輪在場——搬 nested/path-scoped 檔、skill/command、hook 或 CI（必須「保證」而非「鼓勵」的，搬 hook 零 context 成本）。
- 排序＝重量 × 實付頻率，「按能還回多少注意力」排（與 RULE-AUDIT §5 同一概念的兩端：那支排正確性建議，本檔排重量建議）。

## §4 產出格式
1. **每輪總付多少**（先給分母，否則單項省 2k tokens 無從判斷值不值）。
2. **建議清單**（照 §3 排序）：每項＝重量／付費時機／理由（命中率＋錯了代價）／具體關法（改哪個檔、哪個 key、要不要重啟才生效）／能還回多少。
3. **Keeping these**：明確不動的＋一句為什麼值——防使用者自己誤砍承重牆。
4. **我測不到的**：不以沉默代表已覆蓋（產品未揭露的內建重量、未實開 session 的推算……逐項列）。
- 估算紀律沿用 RULE-AUDIT §2 等效條款：char÷4 一律標「估算」，不得寫成實測；產品若揭露實際用量，以實測覆蓋估算並註明用了哪個。
- 成本小且與工作匹配 → 照實說「不建議動」；誠實的空清單勝過湊出來的建議。

## §5 動手規範（report-only，沿 RULE-AUDIT §6）
- 純報告任務：不建立／修改／刪除任何檔案、不改設定、不掛／卸任何 server；開跑第一句話先告知「這次只出建議，不動手」。
- 套用哪幾條需使用者點名；套用前先出 diff，不自行 commit。
